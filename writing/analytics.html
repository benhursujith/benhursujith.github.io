Weekly analytics with an agent, without handing it the data

Metric definitions written down, counts computed locally by a script, a model that only sees the aggregates and writes the story, and checks before the numbers ship.

October 2026. 6 minute read.

Every week someone asks how the product did. The raw data is a pile of exports: sign-ups, sessions, questions asked, lessons finished, each a spreadsheet of rows about real people. The tempting shortcut is to drop the exports into a chat and ask a model to write the weekly report.

I don't, for two reasons. The rows are about people who never agreed to have their details sent to a hosted model, and some of the data belongs to my employer. And a model asked to count rows will sometimes count them wrong, confidently, in a way that's hard to spot in a polished paragraph.

I build analytics and AI products at work, and this is the method I use for a weekly report. The short version: a script does the counting on my machine, the model only ever sees aggregates, and it does the part it's good at, which is the writing.

The pipeline

The reporting window works itself out: the script always uses the last complete Monday-to-Sunday week, so there's no date to remember to bump, and a partial week can't sneak in. An override exists for the rare re-run of an old week.

Write the metric definitions down

Most arguments about numbers are arguments about definitions. What counts as active? Does a returning user who signs up again count twice? Does a lesson count as finished at 90%?

Each metric gets a short written definition that the script implements and the narrative refers to. When the definition changes, it changes in one place, with a dated note, and the report says so.

The model only sees aggregates

This is the core of it. The model's input is a table of totals and week-on-week changes, small enough to read at a glance. It's also small in tokens: a few hundred, where the raw exports would be hundreds of thousands, and would crowd out the reasoning.

Given that table and last week's report, a model is very good at the rest. It notices that questions rose while active learners fell, suggests that a smaller group asked more, and phrases it for the people reading. That's analysis I'd otherwise write myself, and it's the bit worth automating.

A privacy test for every line

Before anything goes to a hosted model, or into a summary file, or onto a slide, each line passes one question:

If this leaked, could someone identify a real person, touch money, log in, or get an employer's internal data?

If yes, it stays on the machine. If no, it's fine to share with a hosted model. Try it on these.

Where a model needs to work closer to the data, a small model running locally can do it, because nothing leaves the machine. Hosted models get the aggregates.

Check the numbers before they ship

The model writes well and counts badly. Even with a clean table, it can round a figure the wrong way, swap two numbers, or describe a 5% dip as “sharp”. So the last step is mine: every number in the narrative is checked against the table, and every claim of cause is read as a hypothesis, not a finding.

Numbers that leave the team get more care. On anything public, I use only rounded running totals, rounded down so they never overstate, computed by the same local script with the same rules. No segment splits, no weekly-active counts, nothing that could be reverse-engineered into rows.

The small things that keep it running

  • A preflight beats a postmortem. Most failed weeks were stale exports or an expired login, both visible in one line before the build.
  • Write down the odd failure. One tool only picked up a fresh login after the session was restarted. That went into the agent's memory as a single line, and it's never cost me an hour since.
  • Keep the runbook next to the code. One page: what to run, in what order, what “good” looks like. Any model can follow it, and so can I after a holiday.
