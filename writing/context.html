One file to resume any project

An index file, a paste-in briefing, an append-only log, and a two-minute ritual at each end of a session. A session starts on a few thousand tokens, not the whole history.

October 2026. 7 minute read. Get the files

I open a project I last touched ten days ago. The model in front of me knows nothing about it. I have two bad options. I can paste in the history, which costs tokens and buries the point under old detail. Or I can explain the project again, which costs me. Neither tells the model which questions are settled and which are still open.

My workspace is built around one idea instead:

Every project holds its own resumable state in plain markdown, in a fixed place, in a fixed shape, so any model in any app can be brought up to speed by reading one file.

Everything else in the setup exists to protect that.

The index file

Each project has one index file. It holds the current state, the next three moves and the closed decisions. It's short, and it always has the same shape, so a model never has to hunt.

Two rules keep it useful. State is rewritten, never added to; history belongs in the log. And it has a word budget, a few hundred words. Past that, it's turning into a log.

What a session reads, and what it skips

This is where the time and the tokens are saved. A session starts by reading four things: the workspace rules, the project rules, the index, and the last three log entries. Nothing else, unless the index points at it.

It does not read the whole log. It does not read the briefing, which repeats the index for a different reader. It does not open the design spec unless the next move needs it. Tick the boxes below to see what each choice costs.

The numbers are rough, but the ratio is the point. The default start is a few percent of the window. It leaves the rest for the actual work, and it's cheap enough to do every single time.

A briefing for chats that can't read files

An agent in an editor reads the index. A chat in a browser can't. For those, each project keeps a briefing: under 400 words, self-contained, written to be pasted into any chat.

It's a separate file on purpose. Agents load the index every session; they don't need 400 words written for a cold reader on top of it.

The test is blunt. Paste the briefing into a fresh chat with a different model and ask, “What should I do next, and why?” If the answer is useful with no follow-up questions, it works. If the model asks what the project is, fix the briefing, not the model.

The log, in a shape a script could read

The index says what is true. The log says how it got that way. It's append-only: entries are added, never edited. And every entry has the same shape.

The fixed shape matters more than it looks. Each entry starts with a rule and a dated heading, so “read the last three entries” means the same thing to every model: everything from the third-from-last dated heading to the end. A model can take the tail of the file without reading the rest.

And Decided asks for the reason, because the reason is the one thing version history can't give you back.

The ritual

Two slash commands, one at each end of a session. Click through.

A session that skips the end has failed, whatever else it produced, because the next session will start blind. A hook prints a reminder when an agent stops, in case it forgets.

Light projects get a lighter version

Not everything deserves the full set. Ideas, frozen projects and small script folders get two files: an index with short task and log sections inside it, and the briefing. When an idea turns into active work, it graduates.

Where it goes wrong

The index swells. Under time pressure, agents add a “previous state” section below the current one instead of rewriting it. An index meant to be a few hundred words grows several times over, and every session pays for it. The fix is a word budget in the rules, and moving old state into the log, where history belongs.

Summaries go stale. A weekly “what's live” page is only useful if someone updates it weekly. Mine carries its own rule: a line that's stale two weeks running gets demoted. Dating every claim at least makes the staleness visible.

None of this needs special software. It's markdown in folders, read by whichever model I'm using that day. The context belongs to the project, not to the tool.
