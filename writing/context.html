One file to resume any project

Context management for AI agents: an index file, a paste-in briefing, an append-only log, and a two-minute ritual at each end of a session.

October 2026. 8 minute read.

Every new conversation with a model starts from nothing. The usual fixes are to paste in the history, which costs tokens and buries the point, or to explain the project again, which costs me. Neither tells the model which parts are settled and which are still open.

My workspace is built around one idea instead:

Every project holds its own resumable state in plain markdown, in a fixed place, in a fixed shape, so any model in any app can be brought up to speed by reading one file.

Everything else in the setup exists to protect that.

The index file

Each project has an _index.md. It's short, and it always has the same shape.

---
project: selah
status: active          # active, paused, idea, shipped, frozen
privacy: public         # public, private, confidential
updated: 2026-08-06
---

# Selah

## State (as of 2026-08-06)
Working: interface, pipeline, local generation.
Stubbed: semantic retrieval (tag matching for now).
README is stale; it still calls generation mocked.

## Next 3
1. Real semantic retrieval and a bigger knowledge base.
2. Watch the pipeline for answers that are pastorally wrong.
3. Fix the README.

## Decisions (closed, do not reopen without cause)
- Architecture and design specs are final.

Each section does one job.

  • State is rewritten every session, never appended to. It says what is true now, with a date, so a reader can tell how stale it is.
  • Next 3 is the three smallest actions that resume the work from a cold start. Three, because a longer list is a backlog, and a backlog doesn't tell you where to begin.
  • Decisions is the list of things that are settled. Without it, every new model helpfully reopens the database question.
  • The frontmatter feeds a dashboard. Status and privacy are queryable across every project, and the privacy tier tells an agent what it may send to a hosted model.

A briefing for chats that can't read files

Agents in an editor read the index. A chat in a browser can't. For those, each project keeps a PASTE-ME.md: under 400 words, self-contained, written to be pasted into any chat.

It's a separate file on purpose. Agents load the index every session; they don't need 400 words written for a cold reader on top of it.

The test for a briefing is blunt. Paste it into a fresh chat with a different model and ask, “What should I do next, and why?” If the answer is useful with no follow-up questions, the briefing works. If the model asks what the project is, fix the briefing, not the model.

The log, in a format a script could read

The index says what is true. The log says how it got that way. LOG.md is append-only, and every entry has the same shape.

---

## 2026-09-19 — Approve trades from the phone

- Did: two-way Telegram approvals; heartbeat alert on silence.
- Decided: approvals only from the chat that gets proposals,
  because that chat is the only trusted identity.
- Broke / found broken: proposals expired unapproved all week.
- Left open: live trading stays switched off until the
  go-live checklist is done.

The fixed format matters more than it looks. “Read the last three entries” has to mean the same thing to every model, so each entry starts with a rule and a dated heading. And Decided asks for the reason, because the reason is the one thing git history can't give you back.

The ritual

Two slash commands, one at each end of a session.

Start

  1. Read the root rules, then the project's index and rules, then the last three log entries.
  2. Say what you believe the current state is, in one sentence.
  3. Wait for me to confirm or correct it.

The one sentence is the important part. It costs me five seconds to read, and it catches stale context before any work happens, rather than an hour later.

End

  1. Append a log entry.
  2. Rewrite State and Next 3.
  3. Rewrite the briefing.
  4. Update the date in the frontmatter.
  5. Add any newly settled decision.
  6. If files moved, note old and new paths in the workspace log.

A session that skips this has failed, whatever else it produced, because the next session will start blind. A hook prints a reminder when an agent stops, in case it forgets.

Light projects get a lighter version

Not everything deserves four files. Ideas, frozen projects and small script folders get two: an index with short task and log sections inside it, and the briefing. When an idea turns into active work, it graduates to the full set.

Spending context carefully

  • Read the tail, not the log. My busiest project log is over 13,000 words. Agents read the last three entries, a few hundred.
  • Keep binaries out. An ignore file stops agents opening PDFs, spreadsheets, databases and vendored code unless I ask.
  • Point, don't paste. Rules link to design documents rather than repeating them.

Where it goes wrong

Two failures show up again and again.

The index swells. State is meant to be rewritten. Under time pressure, agents add “State (superseded)” sections below the current one instead, and an index that should be 400 words becomes 2,800. The fix is a word budget in the rules and moving old state into the log, where history belongs.

Summaries go stale. A weekly “what's live” page is only useful if someone updates it weekly. Mine carries its own rule: if a line is stale two weeks running, demote it. Dating every claim (“as of 6 August”) at least makes the staleness visible.

None of this needs special software. It's markdown in folders, opened in Obsidian, read by whichever model I'm using that day. That's the point: the context belongs to the project, not to the tool.
