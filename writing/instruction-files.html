How I write instruction files for AI agents

Rules files layered by folder, where the nearest file wins. What goes in them, what stays out, why each rule carries its reason, and when a rule becomes a hook.

October 2026. 7 minute read. Get the files

I run about a dozen projects with AI agents: product specs and analytics for work, a few side products, church planning, my own finances. Every session starts from zero. The model doesn't know which folder is confidential, which repository is production, or that I've already decided not to use a database. Without written rules, I say the same things every morning, and on the morning I forget, the agent does the wrong thing confidently.

Instruction files are how I stop repeating myself. Most coding agents now look for a rules file in the folder they're working in and read it before they act. This is how I structure mine, after a few months of getting it wrong.

Layers, and the nearest file wins

One rules file for everything grows until nobody reads it, the model included. So I split it by scope, the way a company splits policy from team norms from a project brief. There's a rules file at the top of the workspace, one per area of my life (work, personal, church), and one per project.

Click a folder to see which rules an agent working there would read, from the root down.

Two rules make the layers work. The root is the floor: a project can add rules, but never relax one. The nearest file wins on everything else, so a project can override an area's default when it has a reason.

One practical wrinkle: different tools look for different file names. I keep one rules file per folder and, next to it, a one-line pointer file that a particular tool loads automatically and that simply imports the rules file. One source of truth, whichever model I open that day.

What goes in a project's rules

Every project's rules file has the same four parts, from a template.

Guardrails aren't style preferences. They're the things a future session would plausibly get wrong, where the mistake costs something. The useful ones look nothing alike from project to project, which is why they're written per project:

  • A trading bot: “Never add an auto-execution path. The manual approval is the product.” An agent's instinct is to automate the slow step. Here the slow step is the point.
  • Health plans: “Never soften the safety items.” Every rewrite sands a warning down a little, and three passes later “see a doctor first” has become “consider checking in.”
  • Learning an instrument: “Don't add scaffolding. More structure is the avoidance mode.” The agent's best skill, organising, is the wrong help.
  • A production codebase: “Read-only.” Two words, and the most important rule in the workspace.
  • Talks and teaching: “Content plan in markdown first, slides second.” Otherwise the thinking ends up trapped in a deck.

Write the reason next to the rule

A rule without a reason gets applied too literally or not at all. With the reason, a model can handle the case I didn't foresee.

What stays out

The workspace rules are loaded at the start of every session in every project, so every line in them is paid for again and again. That makes leaving things out a real skill.

When a sentence isn't enough

Prose is advice. Models follow it most of the time, and most of the time is fine for style. It's not fine for leaking an account number. For the handful of rules where one slip is unacceptable, I use the tool's own enforcement.

  • Permission rules deny reads of saved login sessions and large binaries outright. That's a privacy guard and a token guard at once: an agent can't burn its window on a PDF it didn't need.
  • A pre-write hook refuses any write to a confidential project's summary files if it contains a run of six or more digits. It's crude, and it has caught real mistakes.
  • A stop hook reminds the agent to update the log and index before it ends a session.
  • An ignore file keeps spreadsheets, databases and vendored code out of the agent's reading, so context goes to the notes that matter.

Hooks have a cost: they match hard-coded paths. Add a confidential project and forget the hook, and the protection silently doesn't apply. So the rules say, in bold, that adding a confidential project means editing the hook too. A rule that protects a rule.

A checklist

  1. Is there a root rules file that every project inherits and can't weaken?
  2. Does each project's rules file say how to run it, what not to break, and what to read first?
  3. Does every guardrail describe a real mistake with a real cost?
  4. Does each important rule carry its reason?
  5. Is anything that must never happen enforced by the tool, not only written down?
  6. Is there one rules file, read by every model, rather than one per tool?
