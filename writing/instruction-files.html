How I write instruction files for AI agents

A layered set of rules, one file per folder. What goes in them, what stays out, and when a rule needs a hook instead of a sentence.

October 2026. 9 minute read. Get the files

I run about a dozen projects with AI agents: product specs and analytics for work, a few side products, church planning, my own finances. Every one of those sessions starts from zero. The model doesn't know which folder is confidential, which repo is production, or that I've already decided not to use a database.

Instruction files are how I stop repeating myself. The convention is an AGENTS.md file that agents read before they work. Most coding tools now look for one. This is how I structure mine, after a few months of getting it wrong.

Layers, and the nearest file wins

One instruction file for everything grows until nobody reads it, the model included. So I split it by scope, the way a company splits policy from team norms from a project brief.

Two rules make the layers work. The root is the floor: a project can add rules, but never relax one. The nearest file wins on everything else, so a project can override a domain default when it has a reason.

Next to each AGENTS.md sits a CLAUDE.md that contains a single line, @AGENTS.md. Claude Code loads CLAUDE.md automatically, and that import pulls in the shared file. Every other tool reads AGENTS.md directly. One source of truth, whichever model I open.

What goes in a project file

Every project file has the same three sections, from a template. Here is a real one, lightly trimmed.

Guardrails are the part that earns its keep. Not style preferences, but the things a future session would plausibly get wrong, where the mistake costs something. My template says so in a comment, because the temptation is to fill the section with generic advice.

Guardrails for different kinds of work

The useful rules look nothing alike from project to project. That's the point of writing them per project.

  • A trading bot: “Never add an auto-execution path. The manual approval is the product.” A helpful agent's instinct is to automate the slow step. Here the slow step is the whole idea.
  • Health plans: “Never soften the safety items.” Every rewrite pass sands a warning down a little, and after three passes “see a doctor before training” has become “consider checking in.”
  • Learning guitar: “Don't add scaffolding. More structure is the avoidance mode.” The agent's best skill, organising, is exactly the wrong help.
  • A production codebase: “Read-only.” Two words, and the most important rule in the workspace.
  • Work analytics: “Abstract before anything hosted sees it.” Summaries like “about 200 leads reassigned” are fine. Rows are not.
  • Talks and teaching: “Content plan in markdown first, slides second.” Otherwise the thinking ends up trapped in a deck.

Write the reason next to the rule

A rule without a reason gets applied too literally or not at all. With the reason, a model can handle the case I didn't foresee.

My privacy rules are the clearest example. The first version said work projects were confidential. Agents then refused to put architecture notes into a hosted chat, which was absurd. The rule now says classify the data, not the folder, and gives a test:

If this text leaked, could someone identify a real person, touch money, log in, or obtain an employer's internal data? If not, it's private, not confidential.

That one sentence settles cases I never listed.

When a sentence isn't enough

Prose is advice. Models follow it most of the time, and most of the time is fine for style. It's not fine for leaking an account number. For the handful of rules where one slip is unacceptable, I use the tool's own enforcement.

  • Permission rules deny reads of live login sessions and large binaries outright.
  • A pre-write hook refuses any write to a confidential project's summary files if it contains a run of six or more digits. It's crude, and it has caught real mistakes.
  • A stop hook reminds the agent to update the project log before it ends a session.
  • An ignore file keeps PDFs, databases and vendored code out of the agent's reading, so context goes to the notes that matter.

Hooks have a cost: they match hard-coded paths. Add a confidential project and forget the hook, and the protection silently doesn't apply. So the rule file says, in bold, that adding a confidential project means editing the hook too.

What stays out

  • Anything the model already does well. “Write clean code” is noise.
  • History. Incidents go in the log. Only the lesson goes in the rules, in its durable form. More on that in the memory piece.
  • Current state. What's broken this week changes too often. It belongs in the project index, which gets rewritten every session.
  • Long explanations. If a rule needs a page, link to the page.

A checklist

  1. Is there a root file that every project inherits and can't weaken?
  2. Does each project file say how to run it, what not to break, and what to read first?
  3. Does every guardrail describe a real mistake with a real cost?
  4. Does each important rule carry its reason?
  5. Is anything that must never happen enforced by the tool, not only written down?
  6. Is there one file, read by every model, rather than one per tool?
