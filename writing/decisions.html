Closed decisions, so models stop reopening them

A one-line record for each settled question: the decision, why, when, and what would reopen it. Where they live, how they rotate out, and what a good one looks like.

October 2026. 6 minute read. Get the files

I ask a model to tidy up a small web project. Within a minute it suggests moving to a framework, adding a build step and putting the content in a database. Each suggestion comes with good arguments. I made all three decisions the other way months ago, for reasons that still hold, and I don't remember every reason off the top of my head. So I spend twenty minutes re-arguing a settled question with a very articulate machine.

Models are agreeable and thorough. Ask one to improve something and it will propose the obvious alternatives, which are usually the ones you already ruled out. It isn't being difficult. It just can't see the decision. The fix is to write the decision down where it will be seen.

What a record looks like

Each record is one line, sometimes two, with four parts.

The date does two jobs. It tells a reader how old the reasoning is, and it drives rotation, below. The reopen condition is optional, but it's the part that makes a record age well: it says in advance which change in the world would make the old reasoning wrong.

Compare a record that does none of this with one that does.

Where decisions live

Recent decisions go at the bottom of each project's index file, the one file every session reads. The section heading is itself an instruction:

## Decisions (closed, do not reopen without cause)

Models follow that heading. They still mention an alternative when there's real cause, which is what you want, but they stop proposing the same three ideas every session.

Decisions are written at the end of a session, as part of the same ritual that updates the log and the index. The log entry for that session has a Decided line with the full reasoning; the index gets the one-line version. History in the log, the conclusion in the index.

The life of a decision

Why rotate

The index is read at the start of every session, so every line in it is paid for every time. A project that runs for a year can collect dozens of decisions. Most of the old ones are so settled that nobody, human or model, would think to question them; they've become part of how the project is built.

So decisions older than six months move to a decisions file in the same folder. The index stays short. The old decisions are still there for the rare session that needs them, and a model can be pointed at the file when a question touches old ground.

Six months is a rule of thumb, not a law. The test is whether a fresh model would plausibly propose the alternative. If it would, keep the decision in the index, however old it is.

Good and bad records

What doesn't belong

  • Rules. “Never delete files” applies across the workspace and isn't up for reconsideration. It goes in the rules file, not a project's decisions.
  • Tasks. “We'll add tests” is a plan. Plans go in the next three moves or the task list.
  • Every small choice. If no model would ever propose the alternative, there's nothing to close. A list of trivia buries the decisions that matter.

Try it

Open your most active project. Write down the last three things a model suggested that you'd already ruled out. Give each one line: what you chose, why, the date, and what would change your mind. Put them under a heading that says they're closed. The next session will feel noticeably shorter.
