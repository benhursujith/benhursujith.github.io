Memory that outlives the chat

Where an agent's memory should live, what to keep and what to let go, and how mistakes become rules.

October 2026. 8 minute read. Get the files

Most AI tools now offer memory: the model notes things about you and recalls them later. It's useful, and it has a catch. That memory lives inside one product. Switch models, or open the same project in a different app, and it's gone.

I work across several models and apps, so I treat built-in memory as a cache and keep the real memory where every model can read it: plain files inside each project.

Four kinds of memory

“Memory” covers several different things, and each needs a different home.

Mixing them is the most common mistake I see, in my own files too. History written into state makes the index long and confusing. State written into rules makes rules go stale. Rules buried in a log never get read.

Put memory where every model can read it

My test for where a fact belongs: if I opened this project tomorrow in a different app, with a different model, would it need to know this? If yes, the fact goes in the project's own files. Tool memory is only for things that are genuinely about the tool, like “after logging in to this server, restart the session or the tools won't appear.”

Even then, I copy anything important into the project. Two copies of a fact drift apart, so the project file is the source and the tool memory just points at it.

Decisions are the memory that saves the most time

Models are agreeable and thorough. Ask one to improve a project and it will suggest the thing you ruled out last month, with good arguments. Without a written decision, you spend twenty minutes re-arguing it.

So every index ends with a list headed Decisions (closed, do not reopen without cause). Each entry is one line plus its reason. “Static site over a framework: any agent can edit it, and there's nothing to keep updated.” The heading is an instruction, and models follow it.

Decisions older than six months move out of the index into a separate file. They're still on record, just not loaded every session.

Mistakes become rules

The best rules in my workspace each started as an incident.

When I reorganised the folders, a scheduled job kept pointing at the old path. It failed silently for nearly six days before I noticed. The same afternoon, a work tool's server registration broke for the same reason: a hard-coded absolute path.

The full story went in the log. The lesson went in the rules, in its general form:

Prefer path-independence over path-fixing. Scripts work out their location from their own file. Before moving anything that runs, search for absolute paths in scheduled jobs, launch agents, environments and tool settings.

And the job got a heartbeat that sends an alert when it goes quiet, so silence can't go unnoticed again. The pattern is the same every time: the story in history, the lesson in rules, and where it matters, a check in code.

Forgetting on purpose

A memory system that only adds things gets worse over time. Old facts crowd out current ones, and a model can't tell which is which. Three habits help.

  • Date every claim. “State as of 6 August” tells the reader how much to trust it.
  • Rotate. Logs roll over each year. Old decisions move to their own file.
  • Give summaries an expiry. My weekly “what's live” page says that a line stale for two weeks gets demoted.

Memory and privacy

Some projects hold data that must never reach a hosted model: financial records, personal data about other people, an employer's internal datasets. Their memory files carry abstractions only. “Dining spend up about 15%,” not the statement rows.

That rule is easy to break by accident while writing a summary, so a hook checks it. Any write to those projects' summary files that contains a long run of digits is refused. It's a blunt check, and blunt is right for something this costly.

What I'd tell someone starting

  1. Keep one short state file per project, rewritten every session.
  2. Keep an append-only log, and always write down why.
  3. List settled decisions where the model will see them.
  4. Turn every incident into a rule, and the important rules into checks.
  5. Store memory in plain files you own, not inside one product.
  6. Date things, and retire what has gone stale.
