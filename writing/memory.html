Memory that outlives the chat

The kinds of memory an agent needs, where each one lives, how mistakes become rules, and why a good memory forgets on purpose.

October 2026. 6 minute read. Get the files

Most AI tools now offer memory: the model notes things about you and recalls them later. It's useful, and it has a catch. That memory lives inside one product. Open the same project in a different app, or with a different model, and it's gone. Worse, you can't easily see what it remembers, so you can't tell when it's remembering something that stopped being true.

I work across several models and apps, so I treat built-in memory as a cache and keep the real memory where every model can read it: plain files inside each project.

Four kinds of memory, four homes

“Memory” covers several different things, and each needs a different home and a different way of changing.

Mixing them is the most common mistake I see, in my own files too. History written into state makes the index long and confusing. State written into rules makes rules go stale. Rules buried in a log never get read. Try sorting a few facts yourself.

Put memory where every model can read it

My test for where a fact belongs: if I opened this project tomorrow in a different app, with a different model, would it need to know this? If yes, it goes in the project's own files. Tool memory is only for facts about the tool, or about how I like to work.

How the tool's own memory is kept small

The memory my coding agent does keep is a folder of short notes, plus an index of one line per note. Only the index is loaded each session: a sentence per memory, a few hundred tokens in all. The full note is opened only when its one-line description matches the task. A dozen memories cost almost nothing until one is needed.

Each note has the same shape: what to do, why, with the date and the words that prompted it, and how to apply it. The why matters for the same reason it does in rules. “Read a shared spreadsheet's header row before every write” is a rule. Adding “because someone inserted a column between turns and a batch of rows landed in the wrong cells” tells the model the rule is about other people editing, so it applies it to shared documents too.

Most of these notes are feedback: how I like work done, written down the first time I correct something. Use fewer helper agents. Ship a first version before polishing. Editorial type, not handwriting fonts. Each one saves me from saying it a second time.

Forgetting on purpose

A memory system that only adds things gets worse over time. Old facts crowd out current ones, and a model can't tell which is which. Every stale line also costs tokens on every session that loads it. Three habits help.

  • Date every claim. “State as of 20 October” tells the reader how much to trust it.
  • Rotate. Logs roll over each year into a dated archive file. Decisions older than six months move out of the index into their own file. Still on record, no longer loaded by default.
  • Give summaries an expiry. My weekly “what's live” page says that a line stale for two weeks gets demoted.

And when a memory turns out to be wrong, fix it at the source, rather than adding a correction below it. Two contradicting lines are worse than none.

Memory and privacy

Some projects hold data that must never reach a hosted model: financial records, personal data about other people, credentials, an employer's internal datasets. Their memory files carry abstractions only. “Dining spend up about 15%,” not the statement rows. “Most of the week's sign-ups came from one channel,” not the list of sign-ups.

That rule is easy to break by accident while writing a summary, so a hook checks it. Any write to those projects' index, log or briefing that contains a run of six or more digits is refused, and the agent is told to abstract first. It's blunt, and blunt is right for something this costly.

The tool's own memory follows the same rule. It holds how I work and how the tools behave, never the data.

What I'd tell someone starting

  1. Keep one short state file per project, rewritten every session.
  2. Keep an append-only log, and always write down why.
  3. List settled decisions where the model will see them.
  4. Turn every incident into a rule, and the important rules into checks.
  5. Store memory in plain files you own, not inside one product.
  6. Load an index of memories, not the memories themselves.
  7. Date things, and retire what has gone stale.
