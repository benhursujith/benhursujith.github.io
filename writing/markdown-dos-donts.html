Writing markdown that agents read well

Fixed shapes, one fact per line, real dates, no duplicated facts, short files, the reason next to each rule, and no secrets. Plus why every word in an always-loaded file is paid for on every turn.

October 2026. 7 minute read. Get the files

An agent tells me, confidently, that a bug is still open. It isn't. It was fixed last week, and the note saying so is in the project's files. But so is an older note, two screens up, saying it was “broken since yesterday”. The agent read both, couldn't tell which was newer, and picked the wrong one.

Nothing was wrong with the model. The file was badly written for its reader. Markdown that agents read is a different genre from markdown that people skim: the reader is literal, reads everything you give it, can't ask what you meant, and charges you for every word. These are the habits that have made the most difference in my files.

The rules, as cards

Fixed shapes and headings a script could parse

Every project index in my workspace has the same sections in the same order: a small block of metadata, then State, Next three, Decisions. Every log entry starts with a horizontal rule and a heading with a date. That sounds fussy. It pays off in two ways.

First, instructions become precise. “Read the last three log entries” means exactly one thing when each entry starts with a dated heading: the tail of the file from the third-from-last one. A model doesn't need to read the whole log to find it.

Second, the files become data. The metadata at the top of each index (status, privacy tier, last updated) feeds a dashboard of every project. A hook can find the confidential files by their path and name. None of that works if each file improvises its own layout.

One fact per line, and real dates

Paragraphs are good for arguments and bad for state. When a fact changes, a paragraph has to be rewritten around it, and the old version tends to survive in a clause somewhere. A list of one-line facts can be edited a line at a time.

Relative time is the commonest trap. “Yesterday”, “last week”, “recently” and “currently” are all true the moment they're written and wrong a few days later. Agents write them constantly, because that's how people talk in chat. Ask for absolute dates in the rules, and put an “as of” date on any section that describes the present.

No duplicated facts

The briefing and the index in my projects overlap on purpose: one is for chats that can't read files, the other for agents that can. That's the only duplication I allow, and the briefing is rewritten from the index at the end of every session so they can't drift.

Everywhere else, a fact has one home. Rules point to the design spec instead of repeating it. The index points to the log for history. A memory note points to the project file rather than restating it. Two copies of a fact always drift, and the model will trust whichever it read last.

Every token in an always-loaded file is paid on every turn

Some files are loaded automatically: the rules files at the root and in each project. They're in the context for every message of every session. Caching makes repeated text cheaper, but it still takes room in the window, and it still competes for the model's attention with the work in front of it.

A rough, illustrative sum: a 3,000-token rules file in a session of 40 turns is 120,000 tokens of reading. A 600-token one is 24,000. Same rules, mostly; the difference is what got pasted in “for reference”. Tick what you'd keep in an always-loaded file.

Short files over long ones

A long file has three problems. It costs more to read. The important line sits next to forty unimportant ones, so it gets less attention. And nobody keeps it up to date, so it fills with stale lines that cost even more.

I give the files that are read every session a word budget: a few hundred words for an index, under 400 for a briefing. When one grows past its budget, the cause is almost always history leaking into state. The fix is to move it to the log, not to write more tightly.

The reason next to each rule

“Never add an auto-execution path” is a rule. “Never add an auto-execution path; the manual approval is the product” is a rule a model can reason with. It knows why, so it won't helpfully add a “just this once” shortcut, and it can spot the same risk in a change the rule didn't mention. A reason costs a few words. It's the best value in the file.

No secrets, ever

Markdown notes travel. They get pasted into hosted chats, synced between machines, committed to repositories and shared with colleagues. No password, key, token or account number belongs in one, even briefly. Secrets go in the environment or a password manager, and a note says where to find them, not what they are.

For projects that hold sensitive data, I go one step further. A hook refuses any write to their summary files that contains a run of six or more digits. It's crude, and it catches the account number that slipped into a summary while I wasn't looking.
